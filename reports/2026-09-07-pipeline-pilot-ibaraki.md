# 調査パイプラインのパイロット（茨城県）— スクリプト化でAI依存をどこまで下げられるか

## 1. 調査対象と目的

- 対象: 茨城県44市町村
- 実施日: 2026-09-07
- 目的: 前回調査（`2026-09-06-ibaraki-40-municipalities-stage1.md`）の**定型工程をスクリプト化し、AI依存を下げて近い精度が得られるか**を実測する
- 比較基準: `benchmarks/ibaraki-2026-09-06/`（前回の茨城県225件を凍結したもの）

**このレポートは新しい祭りデータを `data/festivals.json` に追加していない。** 手法の評価だけを行っている。

## 2. 結論（先に数字）

| 指標 | 旧手法（2026-09-06） | 本パイロット |
| --- | --- | --- |
| AI消費トークン | 約55万（Haiku 9本）＋親の統合分 | **0**（S0〜S3・S6はすべてスクリプト） |
| 所要 | AI利用枠5時間をほぼ使い切り | 収集10分＋抽出12分（並列化後・無人・AI枠を消費しない） |
| 出力件数 | 212件追加 | 1595件（未マージ） |
| ベンチマーク再現率 | — | **150/225（66%）** |
| gold（必ず取れるべき34件） | — | **23/34（67%）** |
| 候補ゼロの市町村 | 0/44 | **0/44** |

**AI利用枠の消費をゼロにしたまま、旧手法の出力の66%を再現できた。** 同時に、旧手法が取り逃していた国指定文化財級の行事を複数新たに発見している（§5）。

一方で**34%は再現できていない**。これは手法が旧手法を置き換えられる水準にはまだ無いことを意味する。詳細は §6。

## 3. 何をスクリプトへ移したか

前回レポートを読み返すと、AIが担っていた工程の多くは日本語で明文化されたルールだった。明文化できているならコードで足りる。

| 段階 | 旧手法 | 本パイロット | AI |
| --- | --- | --- | --- |
| S0 台帳 | 都度AIが検索 | 総務省コード表＋ドメイン規則＋HTTP検証 | 不要 |
| S1 発見 | Haiku×固定検索5本/市町村 | トップページから優先度付き探索（検索エンジン不使用） | 不要 |
| S2 抽出 | Haiku | 構造化された位置からの正規表現抽出 | 不要 |
| S3 正規化 | 親モデルが手作業 | 日付3分岐・カテゴリ推定・重複統合・slug | 不要 |
| S4 判定 | 親モデル | `s4_prepare.py` / `s4_apply.py`（**実施済み**） | 要 |
| S6 評価 | 目視 | ベンチマーク突合 | 不要 |

### 検索エンジンを使わずに到達できた

スクリプトには検索エンジンが無い。代わりに自治体サイトの構造を使った。

- 自治体サイトの多くに `sitemap.xml` は**無い**（鉾田市・龍ケ崎市・常陸大宮市・笠間市はいずれも404）
- 一方トップページからは、イベントRSS（`rss.php?mode=news&type=1`）、カテゴリ階層（`page/dir000006.html`）、観光協会サイトへのリンクに機械的に到達できる
- 到達したページの内訳: 計6850ページ（1市町村150ページ上限＋県単位レンズ250ページ）

### 台帳は44/44を自動解決できた

総務省「都道府県コード及び市区町村コード」の読み仮名 → ヘボン式ローマ字 → 自治体ドメインの命名規則（`www.city.<name>.lg.jp` / `www.city.<name>.<pref>.jp` / 同名市がある場合の `ibaraki-koga` 形）で候補URLを組み立て、**実際に取得してページ本文に自治体名があることを確認してから採用**した。推測でURLを書いていない。

読み仮名だけでは母音の重なりが長音（遠野 トオノ→tono）か形態素境界（広尾 ヒロオ→hiroo）か判別できないため、両方の綴りを候補に出してHTTP検証に決めさせている。

観光協会サイトの自動解決は**26/44**（§6.3）。

## 5.5 S4（AI判定）— 唯一AIが要る工程

茨城県の全1595行をAIで判定した。**実測 約15万トークン**（1行あたり約90トークン、1バッチ120行の往復が約11,000トークン）。旧手法は同じ県で約55万トークンを使い `verified` 0件だった。

### 設計 — 判断は委託し、識別子は委託しない

| AIに任せる | 任せない |
| --- | --- |
| 行事か、断片・団体名・一般語か | slug の生成 |
| 同一行事の別名かどうか | **ローマ字化** |
| 県レンズで拾った行事の所在市町村 | カテゴリ推定・日付仕分け |
| 名称の**読み（ひらがな）** | |

AIにはかなの読みだけを返させ、ローマ字化と slug 生成は `romaji.py` が行う。過去にローマ字化を委託して漢字が残ったまま返ってきた事故があるため（前回レポート §9）、識別子そのものは委託しない。

`s4_apply.py` は適用前に必ず機械チェックする — id の過不足、verdict の語彙、`alias_of` の実在・自己参照・keep済み・**循環**、`reading` がかなだけか、生成 slug の形式と重複。**14バッチすべて `--strict` で一発通過した。**

### 名称の整形（S4の後処理・AI不要）

一覧表や投稿ナビ由来の飾りが名称に残る。S2の段階では行事名との区別がつかないが、S4で `keep` と判定できた後なら機械的に落とせる。**元の名称は `aliases` に残すので情報は失われない。**

| 元の名称 | 整形後 |
| --- | --- |
| `ユネスコ無形文化遺産・国指定重要無形民俗文化財「日立風流物」` | `日立風流物` |
| `県指定 富田のささら 所在地 石岡市国府5` | `富田のささら` |
| `4.塚崎の獅子舞` | `塚崎の獅子舞` |
| `三和祇園ばやし（無形民俗文化財）` | `三和祇園ばやし` |
| `新しい投稿 鉾田にぎわい祭り` | `鉾田にぎわい祭り` |
| `亀城太鼓保存会` | `亀城太鼓` |

`保存会` は行事そのものではないが行事の存在を示すため、行事名に寄せて残す。

**整形すると、判定時には見えなかった重複が現れる**（「井草大杉囃子保存会」と「井草大杉囃子」）。同一市町村で整形後の名称が一致し、どちらも別名指定を持たない行は機械的に統合した（8件）。統合後、同名の重複は0件。

この整形により、上記の「2件の見かけの損失」も解消して再現率は S3 と同値に戻った。

### 鹿嶋市について

評価上、鹿嶋市は「1件も再現できなかった市町村」に数えられる。snapshot が鹿嶋市に持つのは「神幸祭」1件だけだからである。しかしパイプラインは**祭頭祭**と**御船祭**を keep している。旧手法のレポート §7-1 が「鹿島神宮の主要祭礼（祭頭祭・式年大祭）を回収できていない」と自認していた、まさにその2件である。

**ここでは再現率が低いことが、こちらの失敗ではなくベンチマークの穴を示している。**


### 5.6 ID方式 — 読めない漢字はハッシュに落とす

slug の生成は当初、読みが確認できた行だけに限っていた。「推測で埋めない」に従った結果だが、keep 871件中645件が `PENDING` のままで、**このままでは登録できない**。

日本の行事名には知らなければ読めない漢字が多い（化蘇沼、鷲子、安居、金砂…）。読みを推測すればIDが誤り、IDの誤りは後から直すとデータの同一性が壊れる。そこで**読めないものはハッシュに落とす**方式に変えた。

| 形 | 条件 | 例 |
| --- | --- | --- |
| ヘボン式ローマ字 | 読みが確認できたとき | `ibaraki-hitachi-hitachinosasara` |
| `x` + SHA-1 先頭8桁 | 読みが確認できないとき | `ibaraki-sakai-x01a1086f` |

ハッシュの種は `都道府県/市町村/名称の照合キー` なので、`第N回`・年号・空白・`祭り`/`まつり`/`祭` の揺れでは変わらない。`x` で始まるかどうかで由来が一目でわかる（日本語のローマ字は `x` で始まらない）。

**一度決めたIDは変えない。** あとから読みが判明してもIDは据え置き、読みは別途記録する。「昇格」させるとIDが変わり、同一性が壊れるため。名称を整形したときも同様にIDは変えない。

結果: 代表行596件すべてにIDが付き、**未確定0 / 重複0**（読み由来211、ハッシュ由来385）。

#### この過程で見つかったバグ

ID重複の検査が1件を捕まえた。「からかさ万灯（フォトギャラリー）」と「土浦桜まつり（フォトギャラリー）」が、どちらも `ibaraki-tsuchiura-fotogyarari` という**同一のIDになっていた**。括弧内のカタカナ「フォトギャラリー」を読みとして採用していたためである。

ふりがなはひらがなで書かれるので、カタカナの括弧書きは読みとして採らないよう修正した。**IDの重複検査が無ければ、2つの別の祭りが同じ識別子で登録されていた。**

## 6. 再現できなかったもの（85件）

### 厳密照合の限界

`snapshot` の85件を再現できていないが、うち**36件は同一市町村内に名称の一部が一致する候補がある**（参考値）。

**この参考値は甘く、過大である。** 中身を確認したところ「雀神社夏季例大祭」に対して「まつり」、「大生神社巫女舞神事」に対して神社の説明文の断片といった誤判定が混じっていた。再現率として使わないだけでなく、件数自体を信用しないこと。

一方で、確実に別名として発見できている例もある。

- 守谷市: snapshot の「守谷祇園祭」に対し **「八坂神社例大祭（祇園祭）」** を出力している
- 龍ケ崎市: gold の「撞舞」に対し **「八坂祇園祭 撞舞」** を出力している

正式名称と通称の対応は AGENTS.md §8 が挙げる典型的な揺れであり、**これを統合するのは S4（AI判定）の仕事である。** 現在の再現率66%は、別名統合を行っていない状態の下限とみるべき。

最終時点でも gold 未ヒット11件のうち5件は、別名で出力されているのに照合できていない: 「撞舞」→「八坂祇園祭 撞舞」、「延方相撲」→「延方相撲（鹿嶋吉田神社祭礼）」、「塔ケ崎十一面観世音大縁日」→「塔ケ崎十一面観世音 縁日大法要祭」など。

### 取りこぼしが大きい市町村

1件も再現できなかった市町村は**1つ（河内町）**まで減り、**候補を1件も出せなかった市町村は0**になった。当初8つ → 観光協会の強化で5つ → XHTML誤認の修正で3つ → 取得枠拡大と県レンズで1つ。

### 取りこぼしの切り分け（40ページ版での実測）

初回の実行（40ページ/市町村）で、取りこぼし177件を機械的に分類した。

| 原因 | 件数 |
| --- | --- |
| 発見(S1)の失敗（ページ自体を取得できていない） | 139（79%） |
| 抽出(S2)の失敗（本文に名前があるのに拾えていない） | 38（21%） |

**発見側が支配的だった。** ここから2つの欠陥を特定して修正している。

1. **探索キューがFIFOだった** — リンクを優先度で採点していたのに、キューが先入れ先出しだったため、優先度の低い浅いページが取得枠を食い潰し、「祭り一覧」のような深い高優先ページに到達できていなかった。優先度付きキューに変更したところ、守谷市は0件から祇園祭・商工まつりの発見に変わった。
2. **抽出が告知文を丸ごと弾いていた** — 「『常陸大津の御船祭』がユネスコ無形文化遺産に…」のように、自治体サイトは行事名を文中に埋める。文ごと弾くと名称まで失われるため、鉤括弧内の固有名を候補に加えた。

この2点の修正で再現率は 26% → 51% になった。

### 6.3 観光協会サイトの解決（14/44 → 26/44）

**robots.txt によるクロール禁止は1件も無かった。** 旧データに現れた観光協会・イベント系ドメイン22件を実測したところ、全件が許可、21件がルートで200を返す。全実行の失敗367件も、288件が404（ドメイン推測の外れ）、66件がDNS解決失敗、403はわずか4件（自治体サイト）だった。**先方の制限はボトルネックではない。**

原因はこちら側に2つあった。

1. **リンクはあるのに拾えていなかった** — 北茨城市はトップページに3本もリンクがあったが、`<img alt="" title="観光協会Youtube">` のように**テキストが `title` 属性**にあり、`alt` しか読んでいなかった。`title` も読み、ホスト名が観光協会を示しかつ自治体名のローマ字を含む場合はリンク文字列に頼らず採用するようにした。
2. **そもそもトップにリンクが無い** — 水戸市・常総市・下妻市・境町。観光カテゴリのページを最大3つだけ辿るようにした。

この修正で 14/44 → 28/44 になり、さらに**Facebook・Instagram を観光協会サイトとして誤採用していた2件**（龍ケ崎市・常陸大宮市）を除いて **26/44** に落ち着いた。SNSは探索の起点を無駄にするうえ robots.txt で拒否される。

観光協会の解決強化により、再現率は 51% → **58%**、gold は 47% → **55%** になった。

### 6.7 クロールの並列化（10時間 → 10分）

150ページ×44市町村を直列で回したところ、**5時間で1市町村しか終わらず**、全体で10時間かかる見込みだった。

原因は設計の誤りで、**礼儀（同一ホストへ1秒間隔）はホスト単位の制約なのに、全市町村を直列に回していた**ため待ち時間が積み上がっていた。自治体ごとに別ホストなので並行して回してよい。

`Fetcher` をスレッドセーフにし（ホストごとのロックで同一ホストへの直列と1秒間隔は維持）、市町村を8並列で探索するようにした。

| | 直列 | 8並列 |
| --- | --- | --- |
| 取得速度 | 11ページ/分 | **577ページ/分** |
| 6850ページの所要 | 約10時間 | **約10分** |

**これは全国展開の可否を左右する。** 1741市町村×150ページ＝約26万ページは、直列なら16日、8並列なら2日である。

なお `extract.py` にも二乗的な処理があった。`context_for` が候補1件ごとにページ全体を再整形しており、1ページに数十候補あるため 6850ページの抽出に10分以上かかっていた。ページ全体の整形を1ページ1回にまとめた。


### 6.8 効かなかった変更（ローマ字パスによる優先付け）

gold の未ヒットを追う中で、**探索の優先度判定が日本語語彙だけで行われている**ことに気づいた。自治体CMSはセクションをローマ字で切る（`/tanoshimu/` `/kankyo_gomi/` `/shisei/`）ため、URLからは何も読み取れていなかった。守谷市では150ページのうち19ページをごみ収集に使い、祇園祭のある `/tanoshimu/` には1ページも入っていなかった。

そこでローマ字の語彙を追加したが、**再現率は 66% → 64% に下がった。** 深さ3・深さ4のどちらでも同じ結果だった。

原因は「優先」側にあった。`bunka` `event` `koen` `gakushu` のような**広すぎる語**が、大きいが収量の低い部分木を引き上げてしまう（守谷市では `bunka_sports_shiminkatsudou` に128ページが集中した）。

切り分けの結果:

| 構成 | 再現率 | gold | 候補ゼロの市町村 |
| --- | --- | --- | --- |
| ローマ字なし・除外は切り捨て | 66% | 67% | 1 |
| ローマ字の優先＋除外・深さ4 | 64% | 64% | 1 |
| ローマ字の優先＋除外・深さ3 | 64% | 64% | 1 |
| ローマ字の除外のみ（優先を無効化） | **66%** | **67%** | **0** |

**採用したのは最後の構成。** ローマ字の「除外」（優先度を下げる）は残し、「優先」は `USE_ROMAJI_BOOST = False` で既定オフにした。コードは残してあるので、他県で再評価すれば判断を見直せる。

もう一点、**除外を「捨てる」から「最後尾に回す」に変えた。** 下妻市はトップページにJS駆動のナビしかなく同一ホストへのリンクが5本だけで、うち3本を除外語が弾いた結果、取得ページがトップ1枚だけになっていた。良いページがある限り選ばれず、他に道が無ければ辿る、という挙動にした。これで**候補を1件も出せない市町村が0になり**、県レンズの所在自動割り当ても41件→69件に増えた。

**この節は「もっともらしいが効かなかった修正」の記録である。** 指摘自体は正しかったが、副作用を測らずに入れた。ベンチマークが無ければ改善として素通りしていた。

### 6.9 ベンチマークのリンク切れ

2026-09-08 に `gold.tsv` の根拠URLを全件確認したところ、**30件中8件（27%）が既に404**だった。旧調査からわずか1〜8日で守谷市と古河市がサイトを再編している。

消滅: 守谷祇園祭、守谷市商工まつり、まつりつくば、筑波山がままつり、古河提灯竿もみまつり、古河花火大会、雀神社夏季例大祭、古河桃まつり。

守谷市の `/tanoshimu/` セクションに到達できなかったのは、**そのセクション自体が消えていた**ためで、クローラーの失敗ではない。

**再現率100%は原理的に到達できない。** 同時にこれは、自治体サイトの祭り情報がこれほど短期間で消えること、つまり構造化して蓄積する価値があることの裏付けでもある。

## 8. 残っている課題

優先順に記す。

1. **観光協会サイトの解決率が26/44。** 残り18市町村のうち、そもそも観光協会がサイトを持たない自治体が一定数あるため、解決率だけで測るのは不適切。リンクを一切張っていない自治体には、県観光連盟の会員一覧のような**上位のリンク集を1本だけ叩く**のが筋が良い。
2. **~~slug の PENDING~~ → 解決した。** ID方式を変えて、読みが確認できない行にはハッシュを与えるようにした（§5.6）。`ID 未確定 0 / 重複 0`。 漢字の読みが確定できないため。「推測で埋めない」に従った結果だが、**IDだけAI依存が残る**という当初の狙いからの後退である。読みの機械的な入手経路（公開辞書・ふりがな）か、読みを必要としないID方式への変更を検討すべき。
3. **S4（AI判定）が未実装。** 別名統合（§6）、対象/対象外の境界判断（§5のノイズ13/30）、所在の帰属、summary生成。ここだけAIが要る。1件あたり数十トークンのバッチ判定なら、1595件でも数万トークンに収まる見込み。
4. **`unclassified` が579件（36%）。** 会場が取れていない候補が多い。S4で会場・主催者を確認すれば大半は分類できる見込みは旧手法と同じ。
5. **抽出の名称品質。** ノイズ13/30のうち4件は「実在する行事だが名称に飾りが残っている」だけで、機械的に直せる。

## 10. 網羅性について
