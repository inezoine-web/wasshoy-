# 調査パイプラインのパイロット（茨城県）— スクリプト化でAI依存をどこまで下げられるか

## 1. 調査対象と目的

- 対象: 茨城県44市町村
- 実施日: 2026-09-07
- 目的: 前回調査（`2026-09-06-ibaraki-40-municipalities-stage1.md`）の**定型工程をスクリプト化し、AI依存を下げて近い精度が得られるか**を実測する
- 比較基準: `benchmarks/ibaraki-2026-09-06/`（前回の茨城県225件を凍結したもの）

**このレポートは新しい祭りデータを `data/festivals.json` に追加していない。** 手法の評価だけを行っている。

## 2. 結論（先に数字）

| 指標 | 旧手法（2026-09-06） | 本パイロット |
| --- | --- | --- |
| AI消費トークン | 約55万（Haiku 9本）＋親の統合分 | **0**（S0〜S3・S6はすべてスクリプト） |
| 所要 | AI利用枠5時間をほぼ使い切り | 実時間 約6時間（無人・AI枠を消費しない） |
| 出力件数 | 212件追加 | 916件（未マージ） |
| ベンチマーク再現率 | — | **116/225（51%）** |
| gold（必ず取れるべき34件） | — | **16/34（47%）** |
| 候補ゼロの市町村 | 0/44 | **0/44** |

**AI利用枠の消費をゼロにしたまま、旧手法の出力の51%を再現できた。** 同時に、旧手法が取り逃していた国指定文化財級の行事を複数新たに発見している（§5）。

一方で**49%は再現できていない**。これは手法が旧手法を置き換えられる水準にはまだ無いことを意味する。詳細は §6。

## 3. 何をスクリプトへ移したか

前回レポートを読み返すと、AIが担っていた工程の多くは日本語で明文化されたルールだった。明文化できているならコードで足りる。

| 段階 | 旧手法 | 本パイロット | AI |
| --- | --- | --- | --- |
| S0 台帳 | 都度AIが検索 | 総務省コード表＋ドメイン規則＋HTTP検証 | 不要 |
| S1 発見 | Haiku×固定検索5本/市町村 | トップページから優先度付き探索（検索エンジン不使用） | 不要 |
| S2 抽出 | Haiku | 構造化された位置からの正規表現抽出 | 不要 |
| S3 正規化 | 親モデルが手作業 | 日付3分岐・カテゴリ推定・重複統合・slug | 不要 |
| S4 判定 | 親モデル | **未実装（AIが要る唯一の工程）** | 要 |
| S6 評価 | 目視 | ベンチマーク突合 | 不要 |

### 検索エンジンを使わずに到達できた

スクリプトには検索エンジンが無い。代わりに自治体サイトの構造を使った。

- 自治体サイトの多くに `sitemap.xml` は**無い**（鉾田市・龍ケ崎市・常陸大宮市・笠間市はいずれも404）
- 一方トップページからは、イベントRSS（`rss.php?mode=news&type=1`）、カテゴリ階層（`page/dir000006.html`）、観光協会サイトへのリンクに機械的に到達できる
- 到達したページの内訳: index 2362 / feed 86 / sitemap 75 / seed 58（計2581ページ）

### 台帳は44/44を自動解決できた

総務省「都道府県コード及び市区町村コード」の読み仮名 → ヘボン式ローマ字 → 自治体ドメインの命名規則（`www.city.<name>.lg.jp` / `www.city.<name>.<pref>.jp` / 同名市がある場合の `ibaraki-koga` 形）で候補URLを組み立て、**実際に取得してページ本文に自治体名があることを確認してから採用**した。推測でURLを書いていない。

読み仮名だけでは母音の重なりが長音（遠野 トオノ→tono）か形態素境界（広尾 ヒロオ→hiroo）か判別できないため、両方の綴りを候補に出してHTTP検証に決めさせている。

観光協会サイトの自動解決は**14/44**にとどまった。ここは弱い（§6）。

### 日付は推測していない

AGENTS.md §5 の3分岐をそのままコード化した。「毎年」「第N」「旧暦」「上旬/中旬/下旬」を含むものだけを `usual_schedule` に入れ、特定年の日付と裸の月日は `null` にして原文を `date_note` に退避する。

実装中に、「毎年行われている市民の祭典」のような**日付を含まない文を日程として採用してしまう**欠陥を見つけて修正した。現在は実際の日付語を伴う場合のみ採用する。`毎年7月中旬から8月中旬`、`毎年4月上旬` のような範囲表現も途中で切らずに取れている。

## 6. 再現できなかったもの（109件）

### 厳密照合の限界

`snapshot` の109件を再現できていないが、うち**38件は同一市町村内に名称の一部が一致する候補がある**。行事としては発見できているが別名で照合できないケースである。

典型例が守谷市で、評価上は「1件も再現できなかった市町村」に数えられているが、実際には次を出力している。

- **八坂神社例大祭（祇園祭）** ← snapshot の「守谷祇園祭」
- **守谷市商工会まつり きらめき守谷夢彩都フェスタ** ← gold の「守谷市商工まつり～きらめき守谷夢彩都フェスタ～」

**この38件を別名として正しく統合するのは、まさに S4（AI判定）の仕事である。** 現在の再現率51%は、別名統合を行っていない状態の下限とみるべき。

### 取りこぼしが大きい市町村

1件も再現できなかった市町村は8つ: 守谷市・北茨城市・東海村・龍ケ崎市・取手市・稲敷市・河内町・鉾田市。出力件数が特に少ないのは 取手市2件・北茨城市2件・八千代町2件・龍ケ崎市4件・高萩市5件。

**主因は観光協会サイトの解決率（14/44）** と見込まれる。旧手法では観光協会が最大の情報源（212件中81件）だった。自治体公式サイトだけでは、観光協会側にしかない行事に届かない。

### 取りこぼしの切り分け（40ページ版での実測）

初回の実行（40ページ/市町村）で、取りこぼし177件を機械的に分類した。

| 原因 | 件数 |
| --- | --- |
| 発見(S1)の失敗（ページ自体を取得できていない） | 139（79%） |
| 抽出(S2)の失敗（本文に名前があるのに拾えていない） | 38（21%） |

**発見側が支配的だった。** ここから2つの欠陥を特定して修正している。

1. **探索キューがFIFOだった** — リンクを優先度で採点していたのに、キューが先入れ先出しだったため、優先度の低い浅いページが取得枠を食い潰し、「祭り一覧」のような深い高優先ページに到達できていなかった。優先度付きキューに変更したところ、守谷市は0件から祇園祭・商工まつりの発見に変わった。
2. **抽出が告知文を丸ごと弾いていた** — 「『常陸大津の御船祭』がユネスコ無形文化遺産に…」のように、自治体サイトは行事名を文中に埋める。文ごと弾くと名称まで失われるため、鉤括弧内の固有名を候補に加えた。

この2点の修正で再現率は 26% → 51% になった。

## 7. 実装中に踏んだ失敗（再発防止のため記録）

| 失敗 | 原因 | 対処 |
| --- | --- | --- |
| 鉾田市の全候補が `dashi`（山車）に分類された | 「鉾田」の**鉾**が山車系の祭り語に一致 | 判定対象から自治体名を除く |
| 「01 岐阜県岐阜市」「卸売市場年報」が大量に候補化 | `市$` が地名と市場に一致 | 市（いち）の複合語のみに限定 |
| 「毎年行われている市民の祭典」が日程として採用された | 「毎年」だけを見ていた | 実際の日付語を伴う場合のみ採用 |
| 「鉾神社夏季例大祭（鉾田の夏祭り」と名称が切れた | 閉じ括弧だけを剥がしていた | 括弧は対で剥がす |
| **クロールが2回、システムのメモリ不足で強制終了** | `cache/` が OneDrive 同期下にあり、7000ファイル・129MBの同期がメモリを食った。Python側にエラーは出ない | `WASSHOY_CACHE_DIR` で同期対象外へ退避 |
| 進捗確認のため `work/pages.tsv` をコピーして、実行中のクロールの出力を壊した | 実行中の出力ファイルを触った | キャッシュが残っていたため再実行で復旧。実行中は触らない |

## 8. 残っている課題

優先順に記す。

1. **観光協会サイトの解決率が14/44。** 旧手法の最大の情報源であり、ここが最大の伸びしろ。公式サイトのリンク文字列・alt・ホスト名で拾っているが不足。自治体サイト内の深い階層や、リンク集ページからの探索が要る。
2. **slug の93%が `PENDING`。** 漢字の読みが確定できないため。「推測で埋めない」に従った結果だが、**IDだけAI依存が残る**という当初の狙いからの後退である。読みの機械的な入手経路（公開辞書・ふりがな）か、読みを必要としないID方式への変更を検討すべき。
3. **S4（AI判定）が未実装。** 別名統合（§6の38件）、対象/対象外の境界判断（§5のノイズ13/30）、所在の帰属、summary生成。ここだけAIが要る。1件あたり数十トークンのバッチ判定なら、916件でも数万トークンに収まる見込み。
4. **`unclassified` が342件（37%）。** 会場が取れていない候補が多い。S4で会場・主催者を確認すれば大半は分類できる見込みは旧手法と同じ。
5. **抽出の名称品質。** ノイズ13/30のうち4件は「実在する行事だが名称に飾りが残っている」だけで、機械的に直せる。

## 10. 網羅性について

**「茨城県を調べ終えた」とは言えない。**

ベンチマーク自体が不完全である（`benchmarks/ibaraki-2026-09-06/README.md`）。旧手法のレポート §7 が挙げた漏れ（鹿島神宮の主要祭礼、地区・町会レベルの祭り全般、県指定無形民俗文化財の一覧2ページ目以降）は、本パイロットでも解消していない。再現率51%はあくまで**旧手法の出力に対する比率**であり、実在する祭りに対する網羅率ではない。

## 11. 次回への提案

1. **観光協会サイトの解決を強化する**（最大の伸びしろ）。自治体サイトのリンク集ページを1階層深く辿る、`kanko`/`kankou` を含むホストへの外部リンクを全て候補にする等。
2. **県教育委員会の指定文化財データベースを、県単位の1レンズとして機械化する。** 旧手法で最も費用対効果が高かった経路であり、ページ送りのURLパターンを特定すれば機械的に完了する。
3. **S4を実装し、916件を対象に別名統合と対象判定を行う。** ここで初めて `festivals.json` へのマージが可能になる。実測トークンを記録して、旧手法の55万と比較する。
4. **slug問題に決着をつける。** 読みを機械的に得るか、ID方式を変えるか。
5. 他県で回して、茨城でのチューニングが過学習でないかを確認する。**茨城の数字だけで手法を評価しない。**
